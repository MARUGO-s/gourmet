# ユーザー管理・承認制

管理者は左メニューの「ユーザー管理」で登録ユーザーの一覧、閲覧の承認・停止、店舗割り当て、管理者任命・解除、削除を行う。

全体管理ページ `https://marugo-s.github.io/multiapp/?admin=users` の「SNS・グルメ」一覧も同じロール・承認状態・許可店舗を参照する。変更後は全体管理ページを再読込する（状態のコピーや別の承認台帳は作らない）。両画面のリンクで行き来でき、`?view=users` はログイン後にユーザー管理を開くための指定に過ぎず、権限を付与しない。Googleログインの戻り先でもこの表示意図だけをsessionStorageで保持する。

全体管理者とグルメ管理者は別権限。全体の一覧を閲覧できても、グルメの承認・任命・削除にはグルメ側で管理者としてログインする必要がある。全体管理ページに新たな書込APIは作らない。連携ビューのmigrationはmultiapp側の`supabase/external-migrations/gourmet/20261007080000_gourmet_user_management_directory.sql`を、このプロジェクトだけに個別適用する。

新規登録（メール・Googleとも）→ 承認待ち・閲覧不可 → 管理者が店舗を選択して「承認して保存」→ 指定店舗だけ閲覧できる。

一般ユーザーはダッシュボードと比較表の閲覧専用。取得依頼・資格情報・店舗設定・通知・AI操作・ユーザー管理は管理者専用。「全店舗」は本人に許可された店舗の合計であり、未割り当ての店舗や他店舗のデータは含まない。承認後もデータの所有者は変更しない。

管理者は全店舗の閲覧とユーザー管理が可能。既存設定の更新には引き続き所有者チェックが適用される。自分自身・最後の管理者は解除不可。管理者の閲覧停止や削除には、別の管理者による権限解除が必要。解除後に店舗割り当てが無い場合は閲覧停止となる。

店舗アカウントの登録状態（サイト・店舗コード・ラベル・版・更新日時）は全管理者で共有する。他の管理者が登録したアカウントも「登録済み」と判定される。ログインID・暗号化パスワードの列権限は開放しない。アカウント一覧で他の管理者の登録は「閲覧のみ」と表示し、削除ボタンは本人の登録だけに表示する。保存・削除・取得依頼などの既存の所有者境界は変更しない。

削除は対象メールの再入力後に完全削除する。AuthはSNSと共有されるため、削除したアカウントでは共有アプリへもログインできなくなる。管理者・店舗/資格情報/分析レポートなどのデータ所有者・他アプリの管理者/ワークスペース所有者は削除を拒否し、閲覧停止を案内する。実在のユーザーはテストで削除しない。

## 認証・データの境界

ブラウザ → JWTを検証するreview-api → 本人JWTでDB RPC/RLS。

- `gourmet_admin_users`: Review Command専用の管理者。SNS側の`social_admin_users`とは独立。
- `gourmet_user_access`: 承認/停止。行が無い場合は承認待ち。
- `gourmet_store_access`: 一般ユーザーに許可された店舗。
- `gourmet_role_audit`: 操作者・対象・変更内容・店舗・時刻。削除後も対象メールを保存。
- 一般ユーザーはこれらの表を直接変更できない。任命/承認/削除RPCは毎回`auth.uid()`の現在の管理者権限を検証し、同じトランザクションロックで権限変更を直列化する。
- 店舗マスタと店舗コードを持つ取り込み行だけ、明示的な店舗割り当てによるSELECTを追加。RLSで所有者条件と割り当て条件を組み合わせ、承認待ち/停止中の本人を拒否する。全店舗を合算した旧データや設定は一般ユーザーへ公開しない。
- `/me`は承認待ちでも本人の状態だけを返す。`/users`・`/users/admin`・`/users/access`・`/users/delete`は管理者RPCで検証。その他のreview-api・ブラウザ向けai-analystは承認状態を先に検証する。
- agent-apiと署名付きM-talk連携は従来の認証を使用する。
- 権限はJWTの古い情報や変更可能なuser_metadataを使用しない。新しいAPI/DBリクエストには直ちに反映。画面は30秒間隔・再フォーカス・手動ボタンで状態を更新し、変更時に表示済みデータを破棄する。

## 配置・検証

migration 025と026（関連データの削除保護）だけを個別適用し、初期管理者は運用時に本人のメールと店舗所有数を照合して025と同一トランザクションで設定する。既存ユーザーの一括承認はしない。review-apiとai-analystを別途配置し、PagesをPR経由で配置する。本番のmigration履歴名は`gourmet_user_management`・`gourmet_delete_data_protection`。

未マージの旧チーム共有案（PR #35、`024_team_members.sql`）とは別設計。旧案は今回適用せず、共通のAPI・画面・RLSを変更するため、この変更の後にそのまま適用/マージしない。担当店舗の設定操作まで共有する場合は、今回の管理者・承認方式に統合してから配置する。

`npm test`、typecheck、build、Edge Functionsのdeno checkに加えて、`server/tests/user-management.integration.sql`をトランザクション内で実行する。テストのユーザー/割り当て/店舗/削除はROLLBACKし、実在ユーザーの状態を維持する。

管理者間の登録状態共有はmigration 027（`gourmet_shared_credential_metadata`）だけを個別適用し、review-apiとPagesを配置する。`server/tests/shared-credential-metadata.integration.sql`で別管理者のメタデータ参照・秘密列拒否・一般ユーザー拒否・権限解除後の即時拒否を検証する（全fixtureをROLLBACK）。

PC/スマートフォンの隔離UIテストは `node scripts/test-user-management-ui.mjs`（Viteを5178番で起動・終了）。認証とAPIをテスト用応答に置換し、本番ユーザーやDBへは通信・変更しない。既存の開発サーバーを使う場合は`GOURMET_UI_TEST_URL`でURLを明示する。PRのCIでも同じテストを実行する。

今後ユーザー・店舗が増えた場合は、一覧のメール検索、割り当て履歴の画面、データ所有者の移管を検討する。
